# v1.7.2 — When green tools still miss the color

> Image2Colors.com · release notes · 2026-08-05

Lighthouse said the button was fine.

Your eyes said otherwise.

Hover **COPY CSS** in dark mode, and the label sank into the panel — a soft purple on a deep purple, pretty in a design file, useless in a real workspace. About **2:1** contrast. WCAG AA wants **4.5:1** for that text. The button looked broken. The audit looked clean.

That gap is the whole story of this release.

---

## What you notice (if you use the app)

In dark mode, **COPY CSS** no longer disappears on hover.

The label and icon stay readable against the results panel. Same click. Same clipboard CSS variables. Just ink that holds up when your pointer lands on it.

Light mode was already fine. We left its character alone and fixed the place that failed under real light — meaning: under a dark theme, on the surface where the button actually lives.

---

## What actually went wrong

Three small lies stacked on top of each other.

**1. The button lied about its color.**  
Hover paint lived on the child label and icon, not on the host `button`. Tools that only read `button { color }` saw the bright default and moved on. The thing you *looked at* was a different color entirely.

**2. The background was transparent.**  
The control sat on `--cards` (the results panel). Contrast is never “text vs button fill” when the fill is glass. It is text vs the panel underneath. Miss that, and the math is fantasy.

**3. The hover color was borrowed.**  
COPY CSS shared a generic icon-button hover path tied to other surfaces. One token change elsewhere, and this control could fail again without anyone meaning to touch it.

Lighthouse did not catch it.  
A lazy contrast check did not catch it.  
A screenshot of the hovered control against its real background did.

---

## What we changed under the hood

### Own tokens for COPY CSS

COPY CSS now owns its surface and ink:

- `--copy-css-btn-color`
- `--copy-css-btn-hover-color`
- `--copy-css-btn-bg`
- `--copy-css-btn-bg-hover`

No more hitchhiking on `--cards-cards-elements`. Dark hover ink moves to a lighter accent that survives on the panel. Light hover keeps the stronger accent where the cream surface can take it.

Icon and label follow `currentColor`. One source of truth. No “host says one thing, children paint another.”

### A contrast gate that looks where you look

Our Playwright AA gate used to sample the wrong paint and, on CI, time out scrolling every button on the page — including ones trapped under an open guide overlay.

v1.7.2 hardens that gate:

- Measure **visible ink** (label text first, then host `color` for icon-only controls)
- Never trust `svg { fill }` on sprite `<use>` icons (Chromium often reports black while `currentColor` is correct)
- Normalize colors through a canvas sample, not a fragile `rgb()` regex
- Resolve the **composited background** up the ancestor chain
- Force hover via stylesheet rewrite in one in-page pass — no per-button scroll/hover circus
- Scope the guide phase to the open overlay only
- Turn **video recording off** in CI (traces stay on failure; movies are a local tool)

Local green and CI green should mean the same thing now.

### Process, not just pixels

We wrote the lesson down so the next UI bug does not start with a doctoral thesis:

1. Ask where the dev server is running (LAN IP, localhost, custom host — never guess).
2. Screenshot the control **and** its background in the failing state.
3. Dump the real computed colors.
4. *Then* touch tokens and tests.

Pretty audits are optional. Readable UI is not.

## For developers skimming this

| Topic | Takeaway |
| --- | --- |
| Symptom | Dark **COPY CSS** hover failed AA; looked washed into the panel |
| Root cause | Child hover ink + transparent button + shared/generic tokens |
| Blind spots | Lighthouse; host-only `color`; SVG `fill` on sprites |
| Fix | Dedicated `--copy-css-btn-*` tokens; `currentColor` cascade |
| Tests | Batched in-page contrast sampling; no CI video; overlay-scoped pass |
| App version | `1.7.2` (package + release tag aligned) |

If you maintain similar icon buttons: **test the painted label on the painted surface in hover**, not the element you find convenient in DevTools.

## Bottom line

v1.7.2 is a small release with a sharp point.

We did not ship a new extraction mode.  
We did not redesign the app.

We made one everyday control honest again — and made our tests fail when the next one lies.

If something still looks wrong on *your* screen, say so. One device, one screenshot, one sentence is enough. That is how this bug got found. That is how the next one will too.
